Google Cloud authentication for the migration tool

The UI uses a service account JSON key (not your user account). The key is sent to the migration tool VM over HTTPS and kept in memory for the session. Disk exports are written to the GCS bucket you name at login; the tool deletes those objects when the job ends.

Minimum IAM: on VM projects — Compute Instance Admin (stop/list) or custom roles with compute.instances.list/get/stop, compute.disks.get, compute.snapshots.create/delete, and snapshot export to Cloud Storage; on the export bucket — storage.objects.create/get/delete/list on the export bucket (e.g. Storage Object Admin on gs://your-bucket/; bucket metadata read is optional).

Before you run anything: set PROJECT_ID to the project that owns your VMs (Cloud Shell shows it in the prompt, e.g. my-gcp-project). The placeholder my-gcp-project is not a real project. That project must have an active billing account (otherwise bucket creation fails with billing account … disabled). You need permission to create service accounts (iam.serviceAccounts.create) — typically Owner or IAM Admin on that project.

Bucket names are globally unique (e.g. oci-migration-bucket is often taken — include your project id). If IAM says the service account “does not exist” right after create, wait a few seconds and run the role bindings again (the script below does that).

Edit the variables below, then copy the commands to your shell (gcloud auth login as that user).

AWS authentication for the migration tool

The UI does not use your personal AWS console login. You log in with an IAM user access key (access key ID, secret, and the EC2 region). The browser sends them to the Migration Tool VM over HTTPS; the Migration Tool signs EC2, EBS and STS requests on your behalf. Credentials stay in memory for the session only (the secret is never stored on disk; access key ID and region may be remembered in this browser).

You need:

  • Permission to list and stop instances and to create, read and delete EBS snapshots (plus EBS Direct ListSnapshotBlocks / GetSnapshotBlock).
  • Outbound HTTPS from the migration tool VM to sts.<region>.amazonaws.com, ec2.<region>.amazonaws.com and ebs.<region>.amazonaws.com.

Edit the variables, then copy the commands into a shell with AWS CLI configured as an admin.

Azure authentication for the migration tool

The UI does not use your personal Microsoft account. You log in with a service principal (an Entra ID app registration plus a client secret). The browser sends tenant ID, client ID and secret to the Migration Tool VM over HTTPS; the Migration Tool exchanges them for a short-lived OAuth token against login.microsoftonline.com and calls Azure Resource Manager on your behalf. Credentials stay in memory for the session only (the secret is never stored on disk; tenant and client ID may be remembered in this browser).

You need:

  • Reader on each subscription that holds VMs (list VMs, disks and sizes).
  • Permission to deallocate VMs and to grant read SAS on managed disks (and create/delete snapshots if you use snapshot capture mode).
  • Outbound HTTPS from the migration tool VM to login.microsoftonline.com, management.azure.com, and Azure blob endpoints (*.blob.core.windows.net, *.blob.storage.azure.net).

Edit the variables in the box below, then use Copy commands to clipboard or run them in Azure CLI (az login as a user who can create app registrations and role assignments). Copy the password from the secret step into the login form; it is shown only once. The default client secret lifetime is 6 months (SECRET_MONTHS).

Instead of the custom role you can assign built-in roles: Virtual Machine Contributor (deallocate), Disk Snapshot Contributor (snapshots and beginGetAccess), and Disk Restore Operator (endGetAccess on disks).

Encrypted VM:

vSphere does not allow exporting an encrypted VM (The operation is not supported on encrypted VM), and the migration tool needs that export to read the disks. A Virtual TPM device can only exist on an encrypted VM, which is why Windows 11 VMs are usually encrypted. Decrypt the VM in vCenter first, the VM's data is not touched:

  1. If BitLocker is enabled in Windows, suspend it first (manage-bde -protectors -disable C: -RebootCount 0, or Control Panel > BitLocker > Suspend protection). The OCI instance gets a different TPM anyway, so BitLocker would otherwise ask for the recovery key after the migration.
  2. Power the VM off in vCenter.
  3. Edit Settings > Virtual Hardware: remove the Virtual TPM device (Windows 11 keeps booting without it once installed).
  4. Edit Settings > VM Options > Encryption: set Encrypt VM to None. If the option is greyed out, the vTPM is still present or the account lacks the Cryptographic operations > Decrypt privilege.
  5. For an encrypted virtual disk: Edit Settings > VM Options > Encryption lists the disks; pick a VM storage policy without encryption for each of them (or change the disk's policy under Virtual Hardware > Hard disk > VM storage policy).
  6. Back in the migration tool, click Refresh in the Source VMs list and start the migration. The OCI instance is still launched as a shielded instance with Secure Boot and a vTPM when the source used Secure Boot.

Optional afterwards: re-encrypt the source VM in vCenter, or keep it as it is for a rollback.
