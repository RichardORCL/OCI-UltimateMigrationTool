# Limitations and troubleshooting

## Known limitations

- **The copy is taken from a stopped VM, or from a snapshot while it keeps running.** Powered-off and powered-on VMs can be migrated. A running VM is stopped (or snapshotted) only after the OCI instance and volumes are prepared, and only after you confirm it by name. There is no live / CBT / incremental sync: changes after the stop or snapshot are not copied. How each source stops the VM is described below.
- **Sources.** VMware vCenter or standalone ESXi, Microsoft Azure, Amazon EC2, Google Compute Engine, or an OVA/OVF/VMDK in Object Storage (see [how-it-works.md](how-it-works.md)). Credentials are entered on the start page, not in the stack. Other hypervisors (Workstation/Fusion, Hyper-V, KVM) are not supported.
- **VMware: the VM must be powered off during the copy.** A powered-on VM is shut down through VMware Tools, with a hard power-off if Tools is not running or the guest has not stopped after `HELPER_GUEST_SHUTDOWN_TIMEOUT_S` (default 300 s). The VM is not powered on again. Suspended VMs and templates are not offered.
- **VMware: encrypted VMs cannot be exported.** vSphere refuses `ExportVm` on a VM with VM encryption (`opUnsupportedOnEncryptedVm`), and a Virtual TPM can only exist on an encrypted VM - so this covers most Windows 11 VMs. The Migration Tool shows the VM as *encrypted* and refuses the job before anything is created in OCI. Decrypt in vCenter first: power off, remove the Virtual TPM (suspend BitLocker inside Windows beforehand), set *Encrypt VM* to *None*, then migrate. On OCI the instance still gets a vTPM when the source used Secure Boot.
- **Azure source: what can be exported.** Azure grants the export SAS the migration tool downloads from only on *managed* disks that are not attached to a running VM, so a job either **deallocates the VM** (consistent copy; the VM is stopped and deallocated right before the export - confirmed by name - and stays deallocated; a VM that is merely *stopped* is deallocated as well) or **snapshots the disks** while the VM runs (crash-consistent, like a power loss; changes after the snapshot are not migrated; the snapshots are billed until the job deletes them). Refused before anything is created in OCI: VMs with unmanaged (storage account) disks, ephemeral OS disks (nothing to export; recreate the VM with a managed OS disk), **Azure Disk Encryption** (the copy would be ciphertext; disable ADE first - server-side encryption with platform or customer-managed keys is transparent and fine), **Confidential VMs** (the OS disk is bound to the confidential guest), disks with `networkAccessPolicy = DenyAll` or `publicNetworkAccess = Disabled` (Azure will not serve the export; disks with `AllowPrivate` work only if their disk-access private endpoint is reachable from the migration tool VM), disks above the 32 TB OCI volume maximum, disks that already have an export SAS granted (`ActiveSAS`; revoke it first), and VMs in a transitional power state. Trusted Launch Secure Boot is matched with a shielded instance like vSphere Secure Boot. Only one VNIC is created; a VM with several NICs gets one. Azure Government / China, Azure Stack, live/CBT sync and user (device-code) login are not supported; the service principal needs *Reader* plus the disk export actions listed in [how-it-works.md](how-it-works.md#microsoft-azure).
- **AWS source: what can be exported.** Only EBS-backed instances. A job either **stops the instance** (consistent copy; confirmed by name; the instance stays stopped) or **snapshots the volumes** while it runs (crash-consistent; snapshots are deleted when the job ends). Refused: instance-store root, Marketplace product codes, terminated or transitional power states, volumes above 32 TB. Encrypted EBS volumes need KMS decrypt/grant on the IAM user. One VNIC is created in OCI.
- **AWS source: after the move.** Linux guests get an optional cleanup that removes Amazon cloud-init drop-ins, disables `amazon-ssm-agent` / EC2 instance-connect units, and prefers the OCI cloud-init datasource. Windows guests need Oracle VirtIO drivers like other sources.
- **Google Cloud: what can be exported.** Persistent disks only (local SSD/scratch is refused). A job either **stops the instance** or **snapshots the disks** while it runs, then exports each snapshot through Cloud Build to your GCS bucket. Confidential VMs export with a warning. Customer-managed disk encryption keys need decrypt permission on the key. One VNIC is created in OCI.
- **Google Cloud: after the move.** Linux guests get an optional cleanup that removes Google cloud-init drop-ins and guest units, and prefers the OCI cloud-init datasource. Windows guests need Oracle VirtIO drivers like other sources.
- **Azure source: after the move.** For **Linux**, the migration tool runs an extra guest fix-up on the copied boot volume (after the disk copy, on the Migration Tool VM): it removes Azure cloud-init datasource drop-ins, disables `walinuxagent` systemd links, comments `/dev/sr0` lines in `fstab`, enables `serial-getty@ttyS0` for the OCI serial console, and prefers the OCI cloud-init datasource. You still may see a short delay on first boot while cloud-init runs; if an instance was migrated with an older tool version, apply those steps by hand or re-migrate. On Windows the *Windows Azure Guest Agent* services can be uninstalled; the Windows guest needs the Oracle VirtIO drivers installed *before* the migration (or *Maximum compatibility*), the same as any other Windows source - Azure VMs have Hyper-V drivers, not virtio. The Linux initramfs and network fix-ups apply as for every Linux source (Azure images normally ship virtio modules, so the initramfs step usually reports *not needed*; the network fix-up gives the renamed NIC DHCP). Azure bills internet egress for the copied data.
- **One availability domain.** Boot volumes cannot leave their AD, so target instances are created in the migration tool's AD. Deploy one migration tool VM per AD if needed.
- **Guest drivers.** The disk content is copied verbatim, with two post-copy fix-ups for Linux (this one and the network one below): RHEL/CentOS/Oracle Linux (and SUSE) often build a *hostonly* initramfs that only contains the source platform's storage drivers, which ends in the dracut emergency shell in OCI (`/dev/mapper/rhel-root does not exist`). Enabled by default (*Rebuild the Linux initramfs with virtio drivers after the copy* under *Advanced*), the migration tool mounts the copied boot volume (plain partitions or LVM; a separate `/boot` is taken from the guest's fstab, whether written as `UUID=`, `LABEL=`, `PARTUUID=`, `/dev/disk/by-*/...` as Ubuntu's installer does, `/dev/mapper/vg-lv` or `/dev/sdXN`) and runs the guest's own `dracut --force --no-hostonly --add-drivers "virtio ..."` in a chroot for every installed kernel whose initramfs lacks virtio modules; it also drops `/etc/dracut.conf.d/oci-virtio.conf` into the guest so later kernel updates keep the drivers. Only the OCI copy is modified. The step is skipped with a reason for Windows, LUKS-encrypted roots, btrfs, guests without dracut (Ubuntu/Debian include virtio anyway) and when the guest's volume group has the same name as one on the migration tool; a failure is reported in the job but does not fail the migration. Windows guests need the [Oracle VirtIO Drivers for Microsoft Windows](https://docs.oracle.com/en/operating-systems/oracle-linux/kvm-virtio/) installed before the export (the export page shows this as an *Important* note for Windows VMs), or use the *Maximum compatibility* preset (IDE + E1000) and install the drivers afterwards.
- **Secure Boot** on the source is matched: the instance is launched as a *shielded instance* from a seed image whose capability schema declares `Compute.SecureBoot`. On VM shapes OCI only offers Secure Boot together with Measured Boot and a vTPM, so all three are enabled (a Windows guest therefore gets a vTPM it may not have had on the source; on bare metal, Linux gets Secure Boot alone). This needs an x86 shape (AMD E-series, Intel Standard3/Optimized3, or bare metal); Ampere A1/A2 shapes are refused up front. Shielded instances cannot be live-migrated by OCI. The guest must boot through a boot loader signed for the Microsoft UEFI CA (shim-based Linux distributions, Windows); a guest that booted with custom Secure Boot keys will not start in OCI.
- **Snapshots** are consolidated by the export (the current disk state is copied); snapshot history is not migrated.
- **Network configuration.** The network interface has a different name in OCI (`ens3`, `enp0s5` or `eth0` instead of the source name), so a profile bound to the old name or MAC never comes up on its own. Enabled by default (*Configure the Linux network for OCI after the copy* under *Advanced: firmware and device model*), the Migration Tool fixes this on the copied boot volume in the same mount session as the initramfs step, without predicting the name: a NetworkManager keyfile profile of `type=ethernet` without `interface-name`/MAC (matches any Ethernet device, IPv4 DHCP, `autoconnect-priority=100`); on guests using the legacy `network.service` a one-shot systemd unit that creates `ifcfg-<name>` with DHCP for every physical NIC without a file on the first boot and then disables itself; a netplan drop-in (`match: name: "e*"`) or a systemd-networkd `[Match] Type=ether` drop-in where those are used; and `*persistent-net.rules` udev rules (which pin a NIC to the source MAC) are disabled with a `.oci-umt-bak` backup. OCI's DHCP always hands out the VNIC's address, also a fixed private IP chosen in the dialog. New files are SELinux-labelled with the guest's own `setfiles` (chroot), else with `setfattr`, else `/.autorelabel` is scheduled. Old profiles are left in place. Skipped with a reason for Windows (the VirtIO adapter uses DHCP), RHEL 6 style guests without systemd (udev rule only) and guests with none of these stacks; a failure is reported in the job but does not fail the migration. Only one VNIC is created.
- **Retries restart a disk from the beginning** (source streams cannot be resumed mid-disk); progress of already copied disks is kept. A job that fails *after* all disks were copied (attach or start rejected by OCI) offers **Retry finalize** in the job view, which re-runs only the attach/start step against the existing volumes.
- **Windows targets get no consistent device paths** (`/dev/oracleoci/oraclevdX` is a Linux feature; OCI rejects the attribute for Windows instances). Data disks show up in Windows in attachment order.
- **Data volumes stay attached as *read/write shareable*.** OCI only attaches data volumes to a running instance, so they are attached while the target still runs from the seed image and the migration tool takes a second, shareable attachment for the copy; the guest then boots with every disk present. The target's attachments keep the shareable flag afterwards (harmless as long as nothing else attaches the volume; detach and re-attach as plain read/write if you want the guard back). With *Maximum compatibility* (emulated attachments, which cannot be shared) the target is started first and the data disks are hot-plugged; with *start after migration* off it is soft-stopped again afterwards.
- **Concurrency** is bounded by the migration tool's 32 attachment slots (`HELPER_MAX_CONCURRENT_JOBS` defaults to 2, adjustable up to 16 on the *Setup* page; further jobs queue).
- **Migration Tool restarts abort running copy jobs.** The export runs on the in-memory source session of the user who started it; after a service restart such jobs are marked `FAILED` and must be cleaned up and restarted. Cloud-source cleanup also releases export access and snapshots, but it needs a login to that source in the browser that cancels; without one the job message lists what is left to release by hand. ISO jobs in *INSTALLING* survive a restart.
- **Seed image import time.** The first job for a new firmware/OS combination waits for a custom image import (minutes). Later jobs reuse the image.
- **Windows licensing** is honoured because the seed image is registered as Windows; OCI applies its own eligibility rules for `OCI_PROVIDED`.
- **Session idle timeout** (`HELPER_SESSION_TTL_S`, 8 h, adjustable on the *Setup* page) logs the browser out, but never interrupts a running migration.
- **Create OCI instance based on ISO relies on undocumented OCI behaviour.** The installer ISO is imported with `CreateImage` and `sourceImageType = VMDK` (the only documented types are `QCOW2` and `VMDK`); OCI recognises the ISO content and an instance launched from such an image boots the ISO as installation media with a blank boot volume of the requested size attached (after the installation the instance boots from the boot volume). This is tested behaviour, not documented. Should OCI change or withdraw it, the import fails on the `iso_image` step (the image enters `DELETED`); the type token is configurable (`HELPER_ISO_SOURCE_IMAGE_TYPE`) in case a dedicated ISO type appears. The ISO flow needs no source login: the web UI runs on an *anonymous* session (created automatically when the page is opened) that can create ISO and OVA jobs, see all jobs, open remote consoles and use the *Setup* page; source VM lists and migration forms require the matching source login. Windows ISOs work, but Windows Setup has no virtio drivers, so the form pre-selects *Maximum compatibility* (IDE + E1000); install the VirtIO drivers afterwards. The shape list includes the Ampere Arm shapes (`VM.Standard.A1/A2/A4.Flex`, `BM.Standard.A1/A2.*`) in their own group: the ISO must then be an aarch64 build, the firmware UEFI (Ampere has no BIOS) and Secure Boot off (no shielded instances on Ampere); the form locks the other choices, the API refuses them. The migration tool cannot tell an x86 ISO from an aarch64 one: an x86 ISO on an Arm shape simply does not boot (blank console). The Arm shape is added to the imported image's compatibility list like a bare metal shape. The migration tool moves no data for these jobs; they survive a service restart in the `INSTALLING` phase.
- **Export OCI instance to OVA/OVF** writes a **separate OVF set** in Object Storage (`.ovf` + one stream-optimized `.vmdk` per disk + `.mf`), not a single `.ova` tarball. Only the **boot volume** is detached from the source; block volumes stay attached and are also attached to the Migration Tool as *shareable* (a non-shareable data attachment is converted first while the instance is still running; emulated attachments cannot be shared and are detached for the copy). The instance is **stopped for the copy and left stopped**; start it again from the OCI console. Only `RUNNING` or `STOPPED` instances can be exported; the migration tool VM itself is refused. Data volumes are included unless the operator unticks *Include attached block volumes*. The tool's IAM policy must already cover the source instance and its volumes (`manage instance-family` / `volume-family` in that compartment); objects are written with the existing Object Storage manage-objects grant. Cancel reattaches the boot volume and does not delete objects already uploaded.
- **OCI Remote Console** (start page) works for any instance in the policy scope of the migration tool VM (`manage instance-family`, which includes `instance-console-connections`); instances outside it are neither listed nor found. The name search uses OCI Resource Search (`query instance resources where displayName =~ '<text>'`, a case-insensitive substring match on the display name, across all compartments the VM may read, at most 200 results) and returns no shape (the search summary carries none). Terminated instances are left out. OCI allows one console connection per instance: a connection that was not created by the migration tool has to be replaced (prompt) or deleted in the OCI console first; connections opened from this page are deleted when the console is closed or idle (`HELPER_CONSOLE_IDLE_TIMEOUT_S`), like the job consoles. A console opened here for a migrated instance and the *Remote console* button of its job share one connection.

## Diagnostics and cleanup

Diagnostics redact URL query strings and common credential fields. They still contain usernames,
resource IDs, hostnames and addresses; review the output before sharing it. Raw HTTP request/response
dumps are disabled even when OCI request logging is enabled.

Cleanup can be retried on cancelled jobs using **Retry cleanup**. Log in to the matching source first
to release snapshots or export access. A failed cloud deletion leaves its resource identifiers in the
job record for the next attempt. Completed migrations cannot be cancelled through this endpoint.

GCP exports must match the source disk's logical size; short or oversized exports fail instead of
silently completing. OVA transfers check cancellation between chunks and close disk and HTTP handles
on failure or cancellation.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Any failed job | *Copy diagnostics* in the job view (`GET /api/jobs/{id}/diagnostics`) collects the job record, the error and the relevant service journal lines as text for a bug report. For OCI `InvalidParameter` errors, enable *Log OCI API requests* on the Setup page and retry. |
| Login fails with *cannot connect to vCenter* | From the migration tool VM: `curl -k https://<vcenter>/sdk`; check routing/VPN, NSG egress and the address/port typed on the login page. |
| Login fails with *the TLS certificate ... could not be verified* | *Verify the server certificate* is ticked but vCenter/ESXi uses its self-signed or VMCA certificate: untick it, or install the issuing CA in the VM's trust store (`update-ca-trust`). |
| Login fails with *invalid user name or password* | Use the vCenter SSO form (`user@vsphere.local` or `DOMAIN\user`); the account must be allowed to log in to vCenter. |
| VM list is empty / a VM is missing | vCenter RBAC: the account needs read access to the VM; templates are hidden. Click *Refresh* (the list is cached for 30 s per session). |
| Azure login fails with `AADSTS7000215` (invalid client secret) / `AADSTS700016` (application not found) / `AADSTS90002` (tenant not found) | Wrong secret *value* (not the secret ID), wrong application (client) ID, or wrong tenant ID / domain; an expired secret gives `AADSTS7000222`. Create a new client secret on the app registration if in doubt. |
| Azure login fails with `AADSTS7000218` / `AADSTS500011` | The app registration is not allowed the client-credentials flow or has no service principal in the tenant (consent). Grant it a role on the subscription (that creates the service principal) or use an app from the same tenant. |
| Azure login fails with *cannot reach login.microsoftonline.com* / *management.azure.com* | The migration tool VM has no internet route: Azure endpoints are not in the Oracle Services Network, so the subnet needs a NAT gateway (or a proxy). `curl -I https://login.microsoftonline.com` from the VM. |
| Azure login succeeds but says *no subscriptions* / *Azure VMs* is empty | The service principal has no role on any subscription. Assign *Reader* on the subscription (and the export actions on the resource groups); role assignments take a minute to propagate. |
| Azure job fails on `beginGetAccess` / `deallocate` / snapshot with `AuthorizationFailed` (403) | The principal lacks the action named in the message (`Microsoft.Compute/disks/beginGetAccess/action`, `virtualMachines/deallocate/action`, `snapshots/write`, ...) on that resource group. Add the custom role from the Azure login page (or *Virtual Machine Contributor* + *Disk Snapshot Contributor* + *Disk Restore Operator* for disk revoke) and start again. |
| **Revoke export access** or job cleanup fails with `disks/endGetAccess/action` (403) | *Disk Snapshot Contributor* grants `beginGetAccess` on disks but not `endGetAccess`. Assign *Disk Restore Operator* on the resource group (or add `Microsoft.Compute/disks/endGetAccess/action` to a custom role), wait a minute, log in again. A subscription Owner can revoke immediately: `az disk revoke-access -g <rg> -n <disk>`. |
| Azure job fails with `OperationNotAllowed ... disk is attached to a running VM` on `beginGetAccess` | The VM was started again between the deallocation and the export, or the deallocate did not complete. Deallocate it in the portal and retry, or use snapshot mode. |
| Azure job: range `GET` returns HTTP 403 repeatedly (`SAS expired or revoked`) | Someone ran `az disk revoke-access` (or the portal's *Revoke export*) while the copy ran, or the disk's network policy changed. The migration tool renews an expired SAS itself; a revoked one fails the disk attempt, which is retried from the start. |
| Azure job: range `GET` returns HTTP 409 / `DenyAll` / `disk access` errors | The disk's *Network access* is *Disable public and private access* or *private endpoint only*; the export only works with public access enabled (or with the disk-access private endpoint reachable from the migration tool VM). Change it on the disk (*Networking*) and retry. |
| Azure job cancelled/failed but the disk still shows *ActiveSAS* or leftover `oci-umt-...` snapshots in Azure | The cleanup ran without an Azure session (Migration Tool restart, session gone). Log in to Azure in the UI and cancel the job again, or release by hand: `az disk revoke-access -g <rg> -n <disk>`, `az snapshot revoke-access ...`, `az snapshot delete ...`. |
| Azure throughput is low | Each disk is downloaded with `HELPER_AZURE_RANGE_WORKERS` (default 4) parallel range requests of `HELPER_AZURE_RANGE_CHUNK_BYTES` (8 MiB); raise the workers to 8-16 on a fast NAT path, and check the OCI NAT gateway bandwidth and the volume tier (*Volume performance*). Only allocated ranges are transferred, so a mostly empty disk is quick regardless of its size. |
| `the availability domain must be the migration tool VM's` | Choose the migration tool VM's AD in the dialog. |
| Seed image stuck in `IMPORTING` | Object Storage policy / bucket; `HELPER_IMAGE_IMPORT_TIMEOUT_S`. |
| `seed image ... entered state DELETED` (import failed) | The error lists the import work request and its OCI-side errors/log. No entries at all usually means the import service could not read the placeholder: it creates a pre-authenticated request on the seed bucket as the migration tool, so the migration tool's policy needs `manage buckets ... where all {target.bucket.name = '<seed bucket>', request.permission = 'PAR_MANAGE'}` (stacks deployed before 0.3.1: re-apply the stack or add the statement by hand; the Audit log shows `CreatePar 404` from `Oracle-JavaSDK` during the import). |
| `ISO image ... entered state DELETED` with `InvalidParameter: Specified namespace or bucket for image import does not exist` | The bucket exists (the picker listed it); this is how OCI reports that the import service may not read it. Same mechanism as the seed import above: the service reads the ISO through a PAR it creates as the migration tool, so the policy needs `read buckets`, `read objects` and `manage buckets ... where request.permission = 'PAR_MANAGE'` on the bucket's compartment. Stacks deployed before the ISO feature only have the seed-bucket statement: re-apply the stack with the current stack zip (only the policy changes; make sure the policy scope covers the bucket's compartment) or add the three statements by hand. If the object exists and the policy is right, OCI may no longer accept an ISO behind the `VMDK` type (see *Known limitations*). |
| `launch_instance ... Shape X is not valid for image Y` | Every custom image carries a list of shapes it may launch on, and an imported image starts with a default list (VM shapes, no bare metal). The migration tool adds the selected shape to the image before launching (`AddImageShapeCompatibilityEntry`); if this still appears, the policy lacks `manage instance-images` on the image's compartment, or the shape does not exist in the region. |
| Remote console: `second SSH hop ... failed: Unable to establish connection` / `VNC channel ... refused` | The tunnel follows the `vncConnectionString` OCI returns (logged in the journal when the connection becomes active). Bare metal instances get a different string (`-L 5900:localhost:5900 <user>@<instance OCID>`); versions before 0.3.2 read the hop-2 host from the `-L` target and tried to reach `localhost:22`. Update the migration tool; if the string has yet another shape, send the journal line. |
| ISO instance does not boot the installer / shows no disk | Check *Launch options* in the job view against the ISO (UEFI vs BIOS; Secure Boot needs a signed boot loader). An installer without virtio drivers (Windows Setup) needs *Maximum compatibility* (IDE + E1000). |
| `target instance entered state TERMINATING` | OCI accepted the launch and failed it asynchronously; the job error now appends the reason from the instance's work request (needs `read work-requests`). DNS host names are unique per subnet: the migration tool checks the subnet's private IPs before launching and uses `name-2`, `name-3`, ... when the VM name is already taken. |
| `cannot open /dev/oracleoci/oraclevdX` / `cannot open /dev/sdX` | The service must run as root (the systemd unit does) and the migration tool VM must use consistent device naming (data volumes); check `lsblk` on the migration tool VM. |
| `boot volume attached to the migration tool VM but its disk was not found` | The boot volume was attached without a device path (OCI does not allow one) and no new whole disk of about the boot volume size showed up in `/sys/block` within `HELPER_VOLUME_TIMEOUT_S` (a few GiB of slack is allowed for `size_in_gbs` vs the kernel). Check `lsblk` on the migration tool and that nothing else attaches volumes to it at the same time. |
| *VM is encrypted* on the export page / `vSphere NotSupported: ... The operation is not supported on encrypted VM` | VM encryption (always the case with a Virtual TPM, i.e. most Windows 11 VMs). Decrypt in vCenter as described under *Known limitations* (remove the vTPM, *Encrypt VM: None*) and migrate again. |
| `NFC lease did not become ready` / `GET ... returned HTTP 4xx` | The account lacks `VirtualMachine.Provisioning.ExportOVF`; or the NFC URL host is unreachable from the migration tool (set `HELPER_NFC_HOST_OVERRIDE` only if lease URLs point at ESXi hosts you can reach). |
| Export throughput is low (~15-25 MB/s) | By default the disk stream is proxied by vCenter, which caps around that rate. Tick *Download the disks directly from the ESXi host* in the migration dialog (migration tool must reach the host shown there on TCP 443 and resolve its name). Also check the VPN/FastConnect bandwidth; a higher *Volume performance (VPU/GB)* in the same dialog raises the write ceiling of the target volumes, and *Decode and write on a separate thread* overlaps the download with inflate/`pwrite` (helps when the migration tool's CPU or the volume, not the network, is the bottleneck). Per disk the stream is a single TCP flow compressed by one ESXi thread, so multi-disk VMs are the only case where more parallelism would help. |
| `direct ESXi download requested but vCenter reports no host for the VM` | vCenter has no `runtime.host` for the VM (orphaned/inaccessible). Fix the VM's placement in vCenter or start the migration without the direct download option. |
| `invalid VMDK stream` / `bad magic` | Something other than a stream-optimized VMDK was returned (a login page or error body); check the lease URL host and proxies between the migration tool and vCenter. |
| Disk retried three times then `FAILED` | Persistent network trouble between the migration tool and vCenter/ESXi; check MTU on the VPN/FastConnect path. |
| Linux target stops in the dracut emergency shell (`dracut-initqueue timeout`, `/dev/mapper/<vg>-root does not exist`) | The initramfs has no virtio drivers. Check the *Initramfs fix-up* row in the job view: if it was skipped or failed (reason given; details in *Copy diagnostics*), power the source VM on, run `echo 'add_drivers+=" virtio virtio_pci virtio_ring virtio_blk virtio_scsi virtio_net "' > /etc/dracut.conf.d/oci-virtio.conf && dracut -f --regenerate-all`, shut it down and migrate again. |
| Linux target boots but has no network (`ip a` shows the NIC without an address) | Check the *Network fix-up* row in the job view: if it was skipped or failed (reason given; details in *Copy diagnostics*), open *Remote console* and configure DHCP on the new interface: NetworkManager `nmcli con add type ethernet con-name oci ifname '*' ipv4.method auto`; legacy network-scripts: create `/etc/sysconfig/network-scripts/ifcfg-<nic>` with `TYPE=Ethernet DEVICE=<nic> BOOTPROTO=dhcp ONBOOT=yes` and `systemctl restart network`. If the profile was written but NetworkManager ignores it, check `ausearch -m avc -ts recent` for an SELinux denial on the keyfile and run `restorecon -Rv /etc/NetworkManager`. |
| Target does not boot | Firmware mismatch (compare *Launch options* in the job view with the source), missing virtio drivers (see the row above; Windows: install the VirtIO drivers or try compatibility mode), or a BIOS guest whose disk uses GPT without a protective MBR. Open *Remote console* in the job view to watch the boot (VNC through the OCI console connection; the migration tool must reach `instance-console.<region>.oci.oraclecloud.com:443`). |
| *Remote console* stays at `Connection lost` / `4502` | The migration tool could not open the SSH tunnel to the console service: no route from the migration tool subnet to `instance-console.<region>.oci.oraclecloud.com:443` (Service Gateway with *All Services in Oracle Services Network*, or NAT gateway; test with `curl -v https://instance-console.<region>.oci.oraclecloud.com` from the migration tool), or the service host key did not match the fingerprint OCI reported (see the migration tool journal). A `foreign_connection` prompt means a console connection created outside the migration tool exists for the instance; replace it or delete it in the OCI console. |
| Job `FAILED` with resources left behind | Inspect in the OCI console (tags `oci-umt-job=<id>`), then *Clean up OCI resources* in the job view (`POST /api/jobs/{id}/cancel`). |
| Job `FAILED: migration tool restarted` | Expected after a service restart; clean up and start the migration again. |

## Manual end-to-end test procedure

1. Deploy the Migration Tool; confirm `/api/health` and open the start page (optional UI password, then the source cards).
2. Pick a source and log in. Confirm the VM list matches that platform's inventory (or pick an OVA / ISO in Object Storage).
3. Start a small Linux test VM (or a small OVA). Expected sequence in the job view: PROVISIONING (seed image on first run) -> EXPORTING with per-disk progress -> FINALIZING -> COMPLETED. For ISO, the job ends in *INSTALLING* and the Remote Console is used to run the installer.
4. In OCI, confirm the instance firmware, launch options and boot volume, and that it boots (use *Remote console* on the job).
5. Repeat with a Windows guest choosing BYOL; confirm `licensingConfigs` and that *Maximum compatibility* is only needed when the guest has no virtio drivers.
6. Test failure paths: start the source VM again before a stop-mode export (job fails with a clear message), cancel a job mid-copy (instance and volumes removed), log out while a job is copying (job completes; log in again to see it).
